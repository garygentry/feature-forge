- **Location:** tech-spec.md §3.4 step 4; §4 Data Model semantics paragraph
- **Issue:** REQ-DEC-06 requires a record on **every** branch, naming three: answered, deferred, and "cancel the run early". §3.4 step 4 says all three "write entries before anything acts on them", and §4 defines the field semantics for exactly two — `answer: <text>` (answered) and `answer: null` + `deferred: true` (deferred). A cancel-early entry has no defined shape. It matters for the REQ-DEC-05 read-back: if cancel-early is written as `deferred: true`, it re-surfaces on the next launch as an outstanding question (probably right); if written as an answered entry, it never re-surfaces and the operator silently loses the branch. The `resolved` gate in §3.2 (a) depends on which is chosen.
- **Suggested fix:** In §4's semantics paragraph, add one sentence fixing the cancel-early shape — recommended: `answer: null`, `deferred: true`, `question` carrying the original needs-human text, and the cancellation rationale recorded in `answer` is *not* used (so it re-surfaces via `decision-list --unapplied` on the next launch, satisfying REQ-DEC-06's "recorded-but-unapplied … MUST be re-surfaced"). If a distinguishing marker is wanted, either add a `cancelled` boolean to the schema in §4 (and to `required`, given `additionalProperties: false`) or state explicitly that cancel-early is recorded as a deferral and needs no distinct field. Mirror the choice in §5.1's `decision-record` flag surface (today `--answer A | --deferred`).
- **References:** PRD REQ-DEC-06, REQ-DEC-05; tech-spec §3.1, §3.2 gate (a), §3.4 step 4, §4, §5.1
- **Checklist:** CHECK-T12, CHECK-T10
